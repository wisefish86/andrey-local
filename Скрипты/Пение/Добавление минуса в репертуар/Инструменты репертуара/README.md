# Инструменты репертуара

Единый контейнер для редких и массовых операций над минусовками.

## Структура

- `Сайт Singer Andrey/` — перескан MP3/ID3 в `data/site/repertoire.json`; внутри лежит `legacy-old-site/` как архив старого сайта.
- `Миграция плюсов/` — dry-run и пакетная загрузка плюсов с записью WOAS.
- `Обновление тегов/` — импорт тегов из CSV.
- `Исправление лирики/` — проверка/исправление встроенной лирики.
- `Распределение минусов/` — распределение папок для Syncthing.
- `Подготовка фонотеки/` — подготовка выбранных MP3.
- `Нормализация аудио видео/` — старый drag-and-drop инструмент ffmpeg.

## Singer Andrey

Запуск:

`Сайт Singer Andrey/Пересканировать репертуар для Singer Andrey.bat`

Сканер читает только MP3-минусовки с `֎` из `paths.library_root`, пропуская Files / Additi0ns / Additions / Editions / staging.

Создаётся:

`../../data/site/repertoire.json`

Экспорт не меняет MP3 и не зависит от конкретной верстки сайта.

## Миграция плюсов

- `Миграция плюсов/Миграция плюсов - ПРОВЕРКА.bat` — dry-run;
- `Миграция плюсов/Миграция плюсов - ПРИМЕНИТЬ.bat` — реальная загрузка и WOAS.

При dry-run дополнительно всегда создаётся:

`../../data/migration_plus_links/ПРОБЛЕМНЫЕ ПАПКИ.txt`

В него попадают папки без плюса, с несколькими кандидатами, с коллизией slug или ошибкой чтения тегов.

Повторный APPLY безопасен:

- если у конкретной минусовки уже есть рабочая WOAS-ссылка, этот MP3 не изменяется;
- если рабочие WOAS есть у всех минусовок папки, FTP-загрузка для этой папки тоже пропускается;
- если часть минусов уже готова, обновляются только оставшиеся;
- временный FTP-сбой получает до 6 внешних попыток с переподключением;
- между внешними попытками применяется растущая пауза: 3 → 6 → 12 → 20 → 20 секунд;
- если все 6 внешних попыток закончились временной FTP-ошибкой, пакет не завершается сразу: до 12 раз делается пауза 60 секунд и повторяется тот же файл; ручной перезапуск нужен только после исчерпания этих восстановительных циклов;
- сама передача идёт небольшими блоками по 64 КБ вместо прежних 256 КБ;
- во время загрузки показываются переданные МБ, процент и средняя скорость;
- подключение к конкретному passive data-порту имеет короткий тайм-аут 5 секунд;
- короткий 5-секундный тайм-аут применяется только к TCP-подключению data-сокета; FTP control-команды (PASV/EPSV/STOR и ответы сервера) используют обычный control timeout 60 секунд;
- после 100% передачи финальный ответ сервера ждётся отдельно до 15 секунд; если сервер его не прислал, скрипт переподключается и до 6 раз проверяет точный SIZE временного файла с паузой 2 секунды;
- если после такого тайм-аута размер временного файла уже точь-в-точь совпал с локальным, повторная загрузка не выполняется — мигратор продолжает с уже переданного файла;
- при несовпадении временного файла лог показывает точные размеры в байтах и разницу, а не только округлённые МБ;
- режим data-соединения адаптивный: следующий файл сначала пробует тот PASV/EPSV, который успешно открылся последним;
- серверный PASV/EPSV-порт теперь печатается в лог;
- если конкретный passive data-порт не открылся, control FTP-сессия не рвётся: на том же соединении до 3 раз запрашивается новый порт; только после исчерпания data-портов и внешнего retry выполняется новый FTP-login;
- один и тот же control-канал после socket timeout не переиспользуется, потому что Python file/socket wrapper после тайм-аута может уже быть непригоден для следующей FTP-команды;
- отдельно различаются этапы открытия data-соединения, передачи байтов и ожидания финального ответа FTP-сервера после передачи;
- если после обрыва временный файл уже успел загрузиться полностью и его размер совпадает, повторно передавать его не нужно — мигратор продолжает с готового временного файла;
- при частично загруженном временном файле в лог выводится его фактический размер, после чего загрузка запускается заново;
- зависшее FTP-соединение закрывается сразу сокетом без дополнительного ожидания команды QUIT;
- если один файл исчерпал все FTP-попытки, APPLY аварийно останавливает весь пакет, следующие файлы не запускаются; уже успешно обработанные изменения сохраняются, а apply-отчёт всё равно формируется.

Параметры находятся в `config.json → migration_plus_links`: `skip_existing_working_woas`, `ftp_retry_attempts`, `ftp_retry_delay_seconds`, `ftp_retry_max_delay_seconds`, `ftp_recovery_cycles`, `ftp_recovery_cooldown_seconds`, `ftp_upload_block_size_kb`, `ftp_progress_interval_seconds`, `ftp_data_connect_timeout_seconds`, `ftp_data_port_attempts_per_mode`, `ftp_data_port_retry_delay_seconds`, `ftp_data_timeout_seconds`, `ftp_final_reply_timeout_seconds`, `ftp_final_reply_recovery_checks`, `ftp_final_reply_recovery_delay_seconds`, `ftp_passive_data_modes`, `abort_batch_on_ftp_retry_exhausted`.

## GUI-комбайн

Все основные операции можно запускать из финального блока **«Инструменты репертуара»** основной программы.

Для инструментов, рассчитанных на drag-and-drop произвольных файлов, есть кнопка **«Открыть все инструменты»**.
